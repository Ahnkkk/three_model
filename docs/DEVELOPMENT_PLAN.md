# 실내 3D 시각화 개발 작업서

- 작성일: 2026-11-19
- 상태: 프로토타입 1차 구현 완료(단계 1~3), 단계 4~5 일부 진행 — 실행 방법·측정 기록은 [README.md](../README.md) 참고
- 기술 구성: Next.js + TypeScript + React Three Fiber + Three.js
- 목적: 웹에서 실내 공간을 탐색하고, 재질·조명·반사가 자연스럽게 표현되는 3D 시각화 구현
- 문서 범위: 개발 계획과 작업 기준. 구현 결과와 참고 측정값은 `README.md`에 기록한다.

## 1. 목표와 개발 방향

Next.js 안에 React Three Fiber(R3F) 기반 3D 화면을 구현한다. 방 구조는 코드 또는 외부 모델로 구성하고, 가구·소품은 기존 에셋을 활용한다.

목표는 베이크된 간접광과 실시간 조명·반사를 조합한 고품질 실내 표현이다. 원문 시리즈의 전체 렌더링 파이프라인은 일부 기능이 제안·개발 중이므로, 사용 가능한 기능부터 단계적으로 구현한다.

R3F는 Three.js를 React 방식으로 다루는 계층이다. `three` 의존성은 계속 필요하며, 고급 조명은 Three.js의 WebGPURenderer와 TSL API를 함께 사용한다.

### 초기 개발 가정

아래 항목은 개발을 시작하기 위한 제안이며, 사용자에게 확정된 요구사항은 아니다.

- 실내 공간 한 개를 먼저 구현한다.
- 초기 품질 검증은 데스크톱 브라우저를 기준으로 한다.
- 가구와 실내 구조는 초기 버전에서 고정한다.
- 사용자는 카메라로 공간을 살펴볼 수 있다.
- 로그인, DB, 사용자 업로드, 별도 GPU 서버는 초기 범위에 포함하지 않는다.
- 사용할 공간의 디자인과 에셋은 구현 전 선정한다. 원문 데모의 에셋을 사용할 수 있다고 가정하지 않는다.

## 2. 구현 범위

### 1차 구현

- 방 한 개의 벽·바닥·천장 구성
- 주요 가구와 소품 배치
- PBR 재질 및 텍스처 적용
- 카메라 회전·확대·축소와 이동 범위 제한
- 직접광과 그림자 적용
- 베이크된 간접광 또는 이에 준하는 기본 조명 구성
- 공간에 맞는 기본 반사 구성
- 로딩 진행 상태, 에셋 로딩 오류, 렌더러 초기화 실패 안내
- 기본 성능 측정과 에셋 최적화

### 후속 구현

- 지역 반사 프로브와 방 사이 반사 전환
- SSR: 화면에 보이는 정보를 이용한 반사
- SSGI: 화면에 보이는 정보를 이용한 간접광 보완
- 조명 프로브를 이용한 움직이는 물체의 간접광
- 시간적 안티앨리어싱 또는 업스케일링
- 모바일 및 WebGL 2용 품질 조절
- 가구 선택·교체·이동, 재질 변경, 조명 제어

### 초기 범위에서 제외

- Lumen과 동일한 실시간 전역 조명 구현
- 벽·가구·조명이 바뀔 때 모든 간접광을 즉시 정확하게 재계산하는 기능
- 다중 사용자 편집과 서버 저장
- 충돌·물리 시뮬레이션과 게임 시스템
- 전체 공간의 자동 생성

## 3. 기술 스택

| 구성 | 용도 | 적용 기준 |
| --- | --- | --- |
| Next.js App Router | 페이지와 애플리케이션 구조 | 기존 프로젝트가 있으면 해당 구조 우선 |
| TypeScript | 컴포넌트·장면 설정·에셋 데이터 타입 | 기본 사용 |
| React Three Fiber | React 기반 장면과 렌더링 생명주기 관리 | 기본 사용 |
| Three.js | 3D 렌더링·조명·재질·로더 | 필수 |
| WebGPURenderer | 고급 조명 구현을 위한 렌더러 | 첫 기술 검증에서 초기화·렌더링 확인 |
| TSL | 노드 재질과 후처리 구성 | 고급 효과 구현 시 사용 |
| @react-three/drei | 카메라 조작·모델 로딩 등 편의 기능 | 사용하는 기능별 WebGPU 호환성 확인 |
| GLB / glTF | 모델 전달 형식 | 기본 권장 형식 |
| Blender 등 | 모델 수정·UV·베이킹·형식 변환 | 필요한 에셋 작업에 사용 |

### 버전 및 호환성 원칙

- 개발 시점에 Next.js, React, R3F, Three.js의 호환 버전을 확인하고 lockfile로 고정한다.
- R3F의 `gl` 비동기 초기화를 통해 WebGPURenderer를 연결하고 초기화를 완료한 뒤 사용한다.
- `three`가 중복 설치되어 서로 다른 인스턴스를 사용하는 상황을 방지한다.
- WebGPURenderer의 후처리는 TSL 기반으로 구성한다.
- 기존 WebGL용 `EffectComposer`, `ShaderMaterial`, `onBeforeCompile` 기반 구현을 그대로 사용할 수 있다고 가정하지 않는다.
- 미병합 PR이 필요한 기능은 별도 실험으로 분리하고, 기본 구현은 해당 기능 없이도 실행되게 한다.
- 개발 브랜치나 포크를 사용할 경우 커밋과 변경 이유를 기록한다.

## 4. 애플리케이션 구조

```text
Next.js 페이지
  └─ 클라이언트 전용 3D 로딩 경계
      └─ R3F Canvas + WebGPURenderer
          ├─ 실내 구조
          ├─ 가구·소품
          ├─ 재질·직접광·베이크된 간접광
          ├─ 반사와 후처리
          └─ 카메라·입력 제어

별도 화면 요소: 로딩 상태, 오류 안내, 필수 조작 UI
```

### 제안 디렉터리

아래 구조로 구현했다. 실제 파일 목록은 `README.md`의 구조 절을 따른다.

```text
src/

      RoomShell.tsx          # 벽·바닥·천장
      SceneAsset.tsx         # 모델 인스턴스 배치
      Lighting.tsx           # 조명·간접광 연결
      Reflections.tsx        # 반사 구성
      Effects.tsx            # 후처리
      CameraControls.tsx     # 카메라 조작
      ViewerStatus.tsx       # 로딩·오류 표시
  config/
    interior.ts              # 배치·조명·품질 설정

    textures/
    lighting/
```

### Next.js 구현 기준

- 브라우저 렌더링 코드는 Client Component 안에서 실행한다.
- 필요한 경우 Client Component 안에서 `next/dynamic`과 `ssr: false`로 3D 모듈을 로드한다.
- 모듈 최상위에서 `window`, `document`, GPU 장치를 직접 참조하지 않는다.
- 프레임마다 변경되는 값은 React 상태 갱신 대신 R3F의 프레임 루프와 참조를 이용한다.
- 장면 재진입·언마운트 시 이벤트와 GPU 리소스를 정리한다. 공유 에셋은 소유 관계를 고려해 해제한다.

## 5. 실내 구성품과 에셋 준비

### 구성품별 확보 방식

| 구성품 | 초기 확보 방식 | 작업 시 확인할 내용 |
| --- | --- | --- |
| 벽·바닥·천장 | 코드로 기본 구조 제작 또는 실내 모델 사용 | 실제 크기, 벽 두께, 표면 방향 |
| 문·창문·계단 | 단순 형태는 코드, 복잡한 형태는 모델 | 개구부와 벽의 연결 |
| 소파·책상·의자 | 기존 모델 활용 | 재질, 크기, 용량 |
| 조명기구 | 기존 모델 + 별도 광원 설정 | 발광 표면과 실제 조명 분리 |
| 책·화분·장식품 | 기존 소품 모델 활용 | 반복 배치와 밀도 |
| 목재·석재·패브릭 | PBR 텍스처 활용 | 실제 표면 크기, 반복, 거칠기 |
| 환경광·기본 반사 | 공간에 맞는 환경 데이터 | 실내와 어울리는 밝기와 색 |

### 에셋 확보 경로

- Poly Haven: 모델, PBR 텍스처, HDRI. 공개 에셋은 CC0.
- ambientCG: PBR 재질, HDRI, 일부 모델. 공개 에셋은 CC0.
- 기존 보유 모델: 형식과 재질을 점검한 뒤 변환.
- Blender 등 외부 도구: 필요한 모델 수정, UV 생성, 베이킹, GLB 출력.

자료의 출처와 사용 조건은 실제 채택하는 에셋별로 기록한다. 특정 사이트에 필요한 모든 가구가 있다고 가정하지 않는다.

### 에셋 도입 절차

1. 공간의 스타일과 실제 크기를 정한다.
2. 주요 가구부터 선정하고 단순한 형태로 배치를 검증한다.
3. 크기 단위와 원점·회전축을 통일한다. 프로젝트 기준은 1 단위 = 1m로 한다.
4. 불필요한 메시와 과도한 텍스처를 정리한다.
5. PBR 재질과 텍스처 경로를 확인하고 GLB/glTF로 준비한다.
6. R3F에서 로드하고 크기·방향·재질·그림자를 확인한다.
7. 필요하면 메시 및 텍스처 압축을 적용하고 해당 디코더를 연결한다.

### 에셋 관리 기준

- 에셋별 파일 경로, 출처, 사용 조건, 크기 단위, 파일 용량을 기록한다.
- 반복 가구는 모델을 재활용하고, 동일 오브젝트의 부모를 바꾸는 문제 없이 인스턴스를 생성한다.
- 최종 에셋 교체에 대비해 배치 설정과 파일 경로를 컴포넌트에 흩어 놓지 않는다.
- 색상 텍스처와 normal·roughness 등 데이터 텍스처의 색 공간을 구분한다.
- Draco, Meshopt, KTX2 압축을 사용하면 각각 필요한 디코더·로더 설정을 함께 검증한다.

## 6. 조명과 반사 구현

### 기본 조명

- 직접광과 그림자를 먼저 맞춘다.
- 광원 수와 그림자 해상도를 제한하고 장면 전체의 노출·톤 매핑을 일관되게 설정한다.
- 벽·바닥 등 고정된 표면에는 베이크된 간접광을 적용하는 방향으로 진행한다.
- 기본 환경 반사를 적용하되, 방 안의 바닥이 실외 풍경만 반사하는 문제를 확인한다.

### 라이트맵 작업

- 고정된 물체에 겹치지 않는 라이트맵용 UV와 충분한 여백을 준비한다.
- 간접광만 베이크할지 전체 확산광을 베이크할지 구분한다.
- 실시간 조명과 베이크 결과가 같은 직접광을 중복으로 더하지 않도록 구성한다.
- GLB 출력만으로 라이트맵이 자동 연결된다고 가정하지 않는다.
- 재질 식별자, 텍스처 경로, UV 채널, 강도 등의 연결 정보를 별도로 저장하고 런타임에 적용하는 방식을 우선 검토한다.
- UV 경계의 이음새와 빛샘을 확인한다.

### 고급 효과 적용 순서

1. 기본 조명과 PBR 재질을 확정한다.
2. AO로 접촉부와 구석의 표현을 보완한다. 베이크된 음영과의 중복을 확인한다.
3. 공간에 맞는 지역 반사를 구성한다.
4. 필요할 때 SSR을 추가하고 화면 밖 정보가 없는 영역의 대체 반사를 연결한다.
5. 동적 오브젝트가 필요할 때 조명 프로브를 추가한다.
6. 성능 여유와 시각적 이점이 확인될 때 SSGI를 검토한다.
7. 선택한 파이프라인에 맞는 시간적 안티앨리어싱 또는 업스케일링을 검증한다.

단계마다 효과를 켜고 끈 결과와 GPU 비용을 비교한다. SSR·SSGI·프로브·환경광을 단순히 더해 조명이 과해지지 않도록 한다.

### 가구·조명 변경의 제한

베이크된 간접광은 기본적으로 고정된 배치를 전제로 한다. 가구 이동이나 광원 변경 후에는 기존 조명 결과가 맞지 않을 수 있다.

초기 버전은 배치를 고정한다. 편집 기능을 추가할 때는 다음 중 요구사항에 맞는 방법을 선택한다.

- 움직이는 물체는 프로브 기반 간접광을 받고, 고정된 공간의 라이트맵을 유지한다.
- 미리 정의한 배치·조명별로 베이크 결과를 준비한다.
- 변경 후 다시 베이크하거나 일부 프로브를 갱신한다.
- 실시간 기법으로 보완하면서 허용 가능한 표현의 차이를 정한다.

SSGI만 추가하면 모든 변경과 화면 밖 간접광까지 정확히 해결된다고 가정하지 않는다.

## 7. 호환성과 성능 기준

### 브라우저 지원

- 초기 기술 검증에서 사용할 브라우저·OS·GPU를 기록한다.
- WebGPURenderer 초기화 성공 여부와 필요한 기능을 실제로 확인한다.
- WebGL 2 대체 실행이 가능하더라도 WebGPU 전용 연산의 동일 동작은 보장하지 않는다.
- 대체 실행 시 무거운 효과를 줄이거나 기본 조명으로 전환하는 방식을 검토한다.
- 지원 불가능한 환경에서는 빈 화면 대신 안내를 표시한다.

아래 값은 실측 결과나 보장이 아닌, 첫 장면을 평가하기 위한 초기 목표다. 기준 기기를 선정한 뒤 조정한다.

최적화는 측정 결과를 기준으로 수행한다. 우선 확인할 항목은 텍스처 해상도, 그림자 수, 반사 캡처 빈도, 후처리 해상도, 드로콜, 반복 모델 재활용이다.
