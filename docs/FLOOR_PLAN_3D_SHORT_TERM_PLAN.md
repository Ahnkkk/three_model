# 도면 → 3D 변환 애플리케이션 단기 개발 계획

- 작성일: 2026-11-24
- 상태: S1~S4 구현(2026-11-24~25, 아래 각 단계의 "구현 결과"). S4는 고정 응답으로 전체 흐름을 검증했고, 실제 모델(Claude·GPT) 호출 검증은 API 키 설정 후 남아 있다. S5는 개발 제안이다.
- 목표: 지원 범위의 도면에서 정보를 추출하고, 사용자가 2D에서 확인·수정한 데이터로 3D를 생성한다.
- 선행 자료: [기존 개발 계획](./DEVELOPMENT_PLAN.md), [사무실 재구성 계획](./OFFICE_RECONFIGURATION_PLAN.md)
- 후속 범위: [장기 개발 계획](./FLOOR_PLAN_3D_LONG_TERM_PLAN.md)
- 일정: 착수일·인력·대상 도면 샘플이 정해지지 않았으므로 기간을 확약하지 않는다. 아래 단계의 의존 순서로 진행한다.

## 1. 현재 상태와 단기 목표

현재 앱은 AI Agent나 이미지 인식 모델을 사용해 도면을 해석하지 않는다. 개발 과정에서 사람이 해석한 수치·가정을 `officePlan.ts`에 작성하고, 이 설정으로 2D와 3D를 생성한다.

`SceneConfig`로 장면을 전달하는 구조와 벽·가구·개구부 생성 기능은 재사용할 수 있다. 단, 도면 변환 함수, 사무실 외곽의 기둥, 2D 치수·영역, 검증 규칙 일부가 `OFFICE_PLAN`에 직접 연결되어 있다. 따라서 입력 파일 업로드만 추가하는 방식으로는 범용 도면을 처리할 수 없다.

### 현재 코드에서 확인한 제약

2026-11-24 코드 대조 결과다. 외벽 두께 0.2m를 실내 치수 바깥에 두는 규칙, 외벽 진행 방향, 도면→월드 변환, 가구 회전 규칙은 아래 규격과 이미 일치한다. 벽 솔리드(모든 방위의 문 홈·창 구멍), 파티션 3D, 보행 충돌, 미니맵, 베이커, 환경맵, 조감도 `fit` 시점은 `SceneConfig`를 인자로 받으므로 재사용한다. 다음 항목은 해당 단계에서 바꿔야 한다.

| 제약 | 위치 | 반영 단계 |
| --- | --- | --- |

S1~S4에서 이 표의 S1~S4 항목을 처리했다(서버 경계는 S4의 `/api/floor-plan/extract`, 각 단계의 "구현 결과" 참고). S5 항목은 남아 있다.

단기 최종 사용자 흐름은 다음과 같다.

```text
도면 이미지 업로드 → 평면도 영역 선택 → 기준 치수 지정
→ AI가 벽·문·창·치수·가구의 초안 추출
→ 단위 정규화 및 검증 → 2D 확인·수정
→ 기본값·미확정 정보 확인 → 기존 엔진으로 3D 생성
→ 정규화한 도면 JSON 내보내기 / 다시 열기
```

AI 호출 없이도 사용자가 벽과 개구부를 직접 지정해 같은 흐름을 완료할 수 있게 한다. AI는 입력 작업을 줄이는 역할이며, 3D 장면의 유일한 데이터 공급원이 아니다.

## 2. 첫 버전의 지원 범위

| 구분 | 단기 지원 범위 |
| --- | --- |
| 원본 | PNG·JPG 평면도 이미지, 표준 도면 JSON |
| 공간 | 단층, 직사각형 외곽, 수평 바닥, 일정한 기본 천장 높이 |
| 내부 벽 | 직선 벽·유리 파티션. 교차·접합 시 중복 면과 틈을 처리 |
| 개구부 | 외벽의 문·창, 내부 벽의 문·바닥에 닿는 통로 |
| 가구 | 기존 종류에 매핑 가능한 가구. 미분류 항목은 명시적인 단순 박스로 대체하거나 제외 |
| 출력 | 공용 데이터에서 생성하는 2D와 3D, 도면 JSON 저장·불러오기 |
| 표시 | 조감도 우선. 실내 탐색은 유효한 시작 위치와 이동 범위가 있을 때 제공 |
| AI | 이미지 이해 모델의 구조화된 초안 추출. 필요할 때 별도 OCR 결합 |

PDF·DXF·DWG·IFC, 다층, L자 외곽, 곡면 벽, 계단, 정밀 광 전달, 협업·계정 기반 저장은 장기 범위다. 지원하지 않는 형상을 직사각형으로 조용히 변형하지 않고 사용자에게 알린다.

## 3. 입력 정보 규격: FloorPlanDocument v1

외부 입력 문서와 렌더링용 `SceneConfig`를 분리한다. 도면 제공자는 카메라·베이크·그림자 설정을 작성하지 않으며, 변환 계층이 해당 설정을 만든다.

아래 규격을 구현의 출발점으로 삼고 S1에서 JSON Schema와 예제로 확정한다. 다음 경로와 이름은 신규 구현 제안이다.

| 데이터 | 필드 제안 | 생성 전 필요한 조건 |
| --- | --- | --- |
| 식별 | `schemaVersion`, `id`, `revision` | 지원하는 형식 버전, 고유 도면 ID, 수정 버전 |
| 단위 | `unit` | 정규화된 문서는 `m`. 원본 단위는 별도 보존 |
| 외곽 | `envelope.width`, `envelope.depth`, `envelope.wallThickness` | 실내 마감면 사이의 폭·깊이, 외벽 두께 |
| 높이 | `ceilingHeight` | 실제값 또는 사용자에게 표시된 기본값 |
| 내부 벽 | `walls[]` | 고유 ID, 시작점·끝점, 두께, 높이, `solid`/`glass` |
| 기둥 | `columns[]` | 선택 사항. 고유 ID, 중심, u·v 방향 크기(천장까지). S1에서 사무실 서쪽 창 사이 기둥을 표현하려고 추가 |
| 개구부 | `openings[]` | 고유 ID, `wallId`, 종류, 벽 시작점에서 중심까지 거리, 폭·높이·하단 높이 |
| 문짝 | `openings[].door` | 문짝 표현 시 경첩 시작/끝, 열림 방향, 각도, 문짝 종류 |
| 가구 | `furniture[]` | 선택 사항. 포함 시 ID, 카탈로그 종류 또는 `unknown`, 위치, 크기, 회전 |
| 영역 | `zones[]` | 선택 사항. 직사각 영역, 이름, 기본 라이브러리의 마감 ID |
| 원본·보정 | `source`, `calibration` | 이미지 입력 시 원본 크기, 선택 영역, 기준점·실제 길이, 원본↔도면 변환 |
| 정보 출처 | `provenance[]` | 필드 경로별 출처·원본 근거·확인 상태. AI 항목은 가능하면 원본 이미지 위치도 보존 |
| 확인 항목 | `issues[]`, `completeness` | 누락·충돌·미지원 항목, 벽/개구부/가구별 확인 상태 |

### 좌표와 치수 기준

- 도면 원점은 외곽 실내 마감면의 왼쪽 위다. 오른쪽 `+u`, 아래쪽 `+v`, 단위는 m다.
- 외곽 폭·깊이는 실내 치수다. 외측 치수 또는 중심선 치수로 들어오면 기준을 식별한 후 변환한다. 기준을 모르면 확인 항목으로 남긴다.
- 내부 벽은 중심선으로 표현한다. 외곽 벽 ID는 `north`, `east`, `south`, `west`로 예약하고 내부 벽 ID와 충돌하지 않게 한다.
- 외곽 벽의 진행 방향은 북: 왼쪽→오른쪽, 동: 위→아래, 남: 오른쪽→왼쪽, 서: 아래→위다. 현재 벽 로컬 좌표와 일치시킨다.
- 개구부의 위치는 소속 벽 시작점에서 중심까지의 거리다. 문은 하단 높이 0, 창은 실제 창 하단 높이를 가진다.
- 가구 위치는 바닥 중심 `[u, elevation, v]`, 크기는 `[width, height, depth]`다. 회전 0은 `+v`를 향하며 양의 Y축 회전은 정면을 `+u` 쪽으로 돌린다.
- 월드 변환은 `x = u - width / 2`, `y = elevation`, `z = v - depth / 2`로 한 계층에서 수행한다.
- 벽 중심선이 외곽 실내 마감면에 접할 때의 벽 두께·접합 규칙을 변환 계층에서 처리한다. 2D와 3D가 다른 보정을 하지 않는다.

### 필수값·기본값·미확정값

폭·깊이·좌표의 실제 배율은 생성 전에 해결한다. 벽 높이·두께는 화면에 표시한 기본값을 적용할 수 있다. 예를 들어 천장 높이 2.8m, 외벽 0.2m, 내부 불투명 벽 0.12m는 초기 제안값이며 실측값이 아니다. 기본값은 프로젝트별로 조정 가능하게 한다.

`provenance`는 값과 별도로 JSON Pointer 형식의 필드 경로를 참조하도록 한다. 예시는 다음과 같다.

```json
{
  "path": "/ceilingHeight",
  "origin": "default",
  "confirmed": false,
  "note": "도면에 높이 표기가 없어 기본값 2.8m 사용"
}
```

출처는 `source`(원본에서 추출), `user`(사용자 입력), `default`(기본값), `derived`(계산값)로 구분한다. AI의 신뢰도 점수가 있더라도 실측 정확도나 사용자 확인 여부와 동일하게 취급하지 않는다.

빈 배열은 확인된 '없음'일 수 있고, 미인식 상태일 수도 있다. `completeness`에 `unreviewed`/`reviewed`를 기록해 두 상태를 구분한다. 가구나 창을 인식하지 못했다는 이유만으로 구조 미리보기를 막지는 않되, 누락 사실을 표시한다.

### 검증 구조

런타임 검증에는 Zod를 사용한다. 2026-11-24 기준 npm `latest`는 4.6.7이며, 설치할 때 기존 의존성처럼 정확한 버전으로 고정한다. 도입 시 설치된 버전의 공식 문서로 아래 기능을 다시 확인한다.

검증은 두 층으로 나눈다.

| 층 | 담당 | 내용 |
| --- | --- | --- |
| 1. 형식 검증 | Zod 스키마 | 필수 필드, 타입, `schemaVersion`·`unit` 허용값, 양수 크기, 열거값(`solid`/`glass`, 개구부 종류, 출처 종류), 배열 항목 수 상한 |
| 2. 문서 검증 | 별도 순수 함수 | ID 중복, 외곽 예약 ID 충돌, `wallId` 참조, 0길이 벽, 개구부 범위 초과·중복, 벽 접합 허용 오차, 외곽 범위 이탈, 기본값·추정값 경고 |

- Zod 스키마를 정본으로 두고 TS 타입은 `z.infer`로, JSON Schema 파일은 `z.toJSONSchema`로 생성한다. 타입·JSON Schema를 손으로 따로 작성하지 않는다.
- 형식 검증 스키마에는 `.refine()`·`.transform()`처럼 JSON Schema로 표현되지 않는 규칙을 넣지 않는다. 그런 규칙은 2층 문서 검증 함수에 둔다. 생성된 JSON Schema와 런타임 검증 결과가 어긋나지 않게 하기 위해서다.
- 1층을 통과한 문서만 2층에 전달한다. 두 층의 결과는 같은 `issues[]` 형식(JSON Pointer 경로, 심각도 `error`/`warning`, 메시지)으로 합친다. Zod 오류의 경로 배열은 JSON Pointer로 변환한다.
- `error`가 하나라도 있으면 장면 변환을 하지 않는다. `warning`은 2D·3D 생성을 막지 않고 화면에 표시한다.
- 같은 스키마를 브라우저(JSON 불러오기·편집 결과)와 서버(AI 응답)에서 함께 쓴다. 검증 모듈은 three.js·React에 의존하지 않는 순수 모듈로 두어 Node 검증 스크립트에서도 실행한다.
- 번들 크기가 문제가 되면 경량 진입점(`zod/mini`)을 측정 후 검토한다.

## 4. 이미지에서 수치와 정보를 얻는 방법

1. 평면도 영역을 선택하고 원본 픽셀 좌표와 선택 영역의 관계를 저장한다. 제목·3D 시안·범례를 평면도와 분리한다.
2. 이미지 이해 모델 또는 OCR로 치수 문자와 단위를 읽는다. 치수선·보조선·화살표를 분석해 숫자가 가리키는 구간을 연결한다.
3. 벽·문·창·가구를 이미지 좌표로 추출한다. 가구 종류만 분류하고 임의로 정밀 모델을 생성하지 않는다.
4. 실제 길이를 아는 기준 구간으로 픽셀 좌표를 m로 정규화한다. 왜곡 없는 이미지에서는 한 구간으로 배율을 구할 수 있으나, 서로 직교하는 두 방향으로 검산하도록 유도한다.
5. 표기 치수, 픽셀에서 계산한 치수, 치수 합계를 비교한다. 불일치하면 근거와 차이를 표시하고 사용자가 기준을 선택하게 한다.
6. 누락된 높이·두께는 입력 또는 기본값으로 해결하고 출처를 기록한다.

원근이 있는 촬영본은 단기 정확도 보장 대상에서 제외하고 정면 스캔본을 요청하거나 수동 보정으로 전환한다. 이미지의 왜곡을 숨기기 위해 가로·세로를 임의로 늘려 맞추지 않는다.

[info.png](../info.png)는 2D와 3D가 섞인 자료이며 오른쪽 치수 합계가 전체 깊이보다 1m 짧다. 평면도 영역 선택과 치수 충돌 표시의 검증 자료로 사용한다. 이 이미지 한 장을 모든 도면 인식 성능의 근거로 사용하지 않는다.

## 5. AI 모델과 Agent의 역할

단기에는 자율 Agent를 도입하지 않는다. 고정된 처리 순서 안에서 이미지 이해 모델에 추출을 요청하고 `FloorPlanDocument` 초안을 반환받는다. 필요하면 OCR 결과를 보조 입력으로 사용한다.

- AI는 추출 초안을 만들고, 프로그램이 형식·좌표·치수·참조 관계를 검증한다.
- AI 출력은 런타임 검증을 통과하기 전까지 장면 설정으로 사용하지 않는다.
- 모델에 의한 재시도는 설정된 횟수·비용·시간 한도 안에서만 수행한다. 실패하면 원본과 수동 입력 내용을 유지한다.
- 키는 서버에 보관하고, 브라우저에서 모델 API를 직접 호출하지 않는다.
- 외부 모델로 이미지를 전송하는 시점과 저장 정책을 제품에 명시한다. 원본·추출 응답을 운영 로그에 무조건 남기지 않는다.
- API 키·연결이 없거나 인식이 실패한 경우 수동 입력과 JSON 가져오기를 제공한다. 성공한 것처럼 빈 도면을 반환하지 않는다.

모델 공급자·모델명·OCR 도입 여부는 샘플 평가 후 결정한다. 특정 SDK나 패키지의 현재 기능을 이 계획에서 확정하지 않는다.

구현 중 정한 규칙:

- `schemaVersion`은 정수 `1`, `unit`은 `"m"`만 허용한다. 모든 객체는 정의되지 않은 필드를 오류로 보고한다. 편집기 검증용 `$schema` 필드만 예외로 허용한다.
- 벽·개구부·기둥·가구·영역 ID는 하나의 이름 공간을 쓴다. `north`·`east`·`south`·`west`는 모든 항목에서 예약한다.
- 필드가 아예 없으면 `schema.required`, 값이 틀리면 `schema.<Zod 코드>`, 문서 검증은 `<대상>.<내용>` 코드로 보고한다. Zod 메시지는 한국어 로캘을 쓴다.
- 접합: 좌표 오차 1mm 이내면 같은 점·같은 선으로 본다. 벽 끝점이 외곽 면이나 다른 벽에서 1mm 초과 5cm 이하로 떨어져 있으면 접합 의도로 보고 틈을 경고한다. 같은 선 위에서 길이가 겹치면 오류, 끝점만 닿는 일직선 연결·T자·X자 교차는 허용한다. 외곽 면 위에 놓인 내부 벽은 오류다.
- 벽 중심선 끝점은 외곽 실내 마감면(0~폭, 0~깊이)까지 올 수 있다. 두께 처리는 S2 변환 계층이 맡는다.
- 이미지 원본(`source.kind = "image"`)은 배율 보정이 필수다. 기준 구간 길이 불일치(1% 초과), 한 방향뿐인 기준 구간, 가로·세로 배율 차이는 경고한다.
- 출처가 `default`·`user`이고 미확인이면 필드별로 경고하고, 미확인 `source` 추출값은 개수를 한 번 경고한다. 해결되지 않은 `issues[]`와 `unreviewed` 목록, 검토 상태 누락도 경고한다.
- 지원 범위 값(외곽 1~60m, 천장 2~6m, JSON 2MB 등)은 초기 제안값이며 S5 평가 후 조정한다.

남은 한계: 생성한 JSON Schema 파일은 Zod 스키마와의 일치만 확인했고 별도 JSON Schema 검증기로 예제를 검사하지는 않았다. 문 열림 영역과 가구 간섭, 가구 겹침은 S1 문서 검증에 넣지 않았다(사무실 전용 `validateOfficeLayout`에 있음, S2에서 일반 검증으로 분리).

구현 중 정한 규칙과 발견한 문제:

- 원본 이미지 보정은 정면 스캔을 전제로 한 등방 배율·평행 이동만 쓴다(회전·원근 없음). 여러 기준 구간의 배율은 평균하고 차이는 문서 검증이 경고한다. 기준 구간으로 계산한 외곽 크기는 `derived`·미확인으로 기록하며, 문서 검증이 미확인 계산값도 경고하도록 바꿨다.
- 내부 벽 창은 추가·이동 단계에서 막는다(단기 지원 범위). 개구부는 벽 범위 안으로 제한하고, 벽을 지우면 그 벽의 개구부도 지운다.
- 빠르게 끌면 마지막 포인터 이동이 상태에 반영되기 전에 놓기 처리가 실행되어 끝점이 짧아지는 문제를 브라우저 검증에서 발견했다. 놓은 위치로 결과를 다시 계산하도록 고쳤다.
- 조명 갱신으로 리소스를 교체하면 인스턴스 메시(화분 잎·책·의자)가 새로 만들어지면서 배치가 초기화되는 문제를 발견했다. 리소스가 바뀌면 인스턴스를 다시 배치하도록 고쳤다.

남은 한계: 베이크는 시간 조각으로 나눴지만 여전히 메인 스레드에서 실행한다(워커 분리는 L6). 편집 화면은 영역·가구 배치·기둥을 편집하지 않는다(가구는 삭제만, L4). 원본 이미지는 저장하지 않으므로 다시 연결해야 한다. 원근이 있는 촬영본은 보정하지 않는다. 좁은 화면(모바일) 조작은 검증하지 않았다.

구현 중 정한 규칙:

- 좌표 체계: 모델은 **보낸 이미지 픽셀**로 본 것을 보고하고, 프로그램이 보낸 이미지 → 원본 픽셀(잘라낸 영역·축소 비율) → 도면 m(사용자 보정 `pixelToPlan`)로 바꾼다. 모델이 배율을 추정하지 않으므로 치수 계산 오류가 좌표에 섞이지 않는다. Claude Opus 5.5는 긴 변 2576px까지 좌표가 픽셀과 1:1이므로 이 크기를 상한으로 쓰고, GPT는 `detail: "original"`로 크기를 바꾸지 않게 요청한다. 서버는 이미지 머리글의 크기와 선언한 크기, 가로·세로 축소 비율이 맞는지 확인한다.
- 응답 형식: 모델 응답 형식(`FloorPlanExtraction`)은 FloorPlanDocument와 별도 스키마지만 같은 원칙으로 Zod를 정본으로 두고 JSON Schema를 생성해 두 공급자에 그대로 보낸다. 두 공급자의 구조화 출력 제약에 맞춰 모든 필드를 필수(값이 없으면 null)로, 숫자·길이 제약 없이, 튜플 대신 객체로 정의했다. 서버는 응답을 같은 Zod 스키마로 다시 검증하고, 제안 전체를 적용한 초안 문서를 S1 검증기(형식 + 문서 검증)로 검증해 결과를 함께 돌려준다.
- 재시도·한도: JSON이 아니거나 형식이 맞지 않거나 출력이 잘리면 이유를 붙여 한 번 더 요청한다(최대 2회). 호출 1회 150초, 요청 전체 240초, 응답 32,000 토큰, 서버 프로세스당 동시 2건·시간당 30건. 모델 거절·판독 불가·추출 항목 없음은 재요청하지 않고 실패로 돌려준다(빈 도면을 성공으로 반환하지 않음). 클라이언트 취소는 서버의 모델 호출까지 중단한다.
- 변환: 외곽선을 다시 그린 벽은 버리고, 3° 안의 벽은 수평·수직으로 펴고, 0.15m 안의 끝점은 합치거나 다른 벽·외곽에 붙인다. 벽에 붙여 그린 가구가 벽 두께 안으로 0.15m 이하로 들어가면 벽 밖으로 민다. 개구부는 두 문설주가 놓인 벽을 찾아 오프셋·폭으로 바꾸고, 문 경첩·열림 방향은 벽 진행 방향 기준으로 바꾼다. 표기 치수는 보정으로 잰 길이와(차이 max(0.1m, 3%) 초과면 충돌), 같은 변의 연속 치수 합계는 전체 치수와(0.05m 초과면 충돌) 대조한다. 단위 표기가 없는 치수는 잰 길이에 가장 가까운 단위로 해석하고 표시한다.
- 확정값 보호: 사용자가 입력했거나 확인한 값, 출처 기록이 없는 값을 바꾸는 제안은 "확정값 변경"으로 표시하고 기본 선택에서 뺀다. 미확인 AI 값의 변경과 새 항목 추가는 기본 선택이다. AI가 찾지 못한 기존 항목은 지우지 않는다. 같은 결과를 다시 받으면 모두 "일치"로 처리해 중복 추가하지 않는다.
- 전송·보존: 키는 서버 환경 변수에만 두고 브라우저는 서버 경계만 호출한다. 앱 서버는 이미지와 응답 본문을 저장하거나 로그에 남기지 않고 공급자·모델·성공 여부·시도 횟수·토큰·소요 시간만 기록한다. OpenAI에는 `store: false`로 요청한다. 공급자 측 보존은 각 공급자의 API 데이터 정책을 따른다.
- 개발 전용 고정 응답: production이 아닐 때 `FLOOR_PLAN_AI_FAKE_FILE`을 지정하면 모든 공급자가 그 파일 내용을 응답으로 돌려준다. 키 없이 화면 흐름을 확인할 때만 쓴다.

확인 결과:

- `verify:ai` 75개 항목 통과. 응답 JSON Schema가 공급자 제약을 지키는지, 좌표 왕복, info.png 고정 응답의 제안(외곽 중복 벽 제거, T·L 접합 맞춤, 두께 환산, 가구 방향, 3.6 + 3.4 ≠ 8.0 합계 불일치, 천장 높이 누락), 차이·적용(소속 벽 연결, 문 방향, 출처·근거 위치 기록, 확정값 보호, 선택 적용, 재적용 시 일치), 적용 결과의 문서 검증·장면 변환·배치 검사, 서버 처리(재요청·거절·판독 불가·빈 결과·인증 오류·취소·시간 초과·이미지 머리글·비율 검사)를 확인한다.
- `verify:floor-plan` 77개, `verify:editor` 44개, `verify:office` 46개, 타입 검사, `next build`가 통과한다.
- 고정 응답으로 띄운 dev 서버에서 헤드리스 Chrome(CDP)으로 확인했다. info.png 업로드 → 보정(10m·8m 기준, 30.6 px/m) → AI 초안(변경 35개 중 기본 선택 34개, 적용 불가 1개, 합계 불일치·천장 높이 누락 표시, 2D 제안 표시) → 가구 1개를 빼고 적용(벽 6·개구부 7·가구 11, 3D 생성) → 실행 취소·다시 실행 → 재추출(남은 가구 1개만 차이) → 추출 중 취소("수동으로 계속"·"다시 시도") → JSON 저장. 저장 파일의 AI 항목 24개가 출처 `source`·근거 위치를 가지고, 다시 열면 오류 없이 통과했다. 페이지 오류는 없었다. 서버 요청을 0.4초 만에 끊으면 서버도 `cancelled`로 끝나는 것을 확인했다.

남은 한계:

- **실제 모델 호출은 검증하지 않았다.** 이 환경에 `ANTHROPIC_API_KEY`·`OPENAI_API_KEY`가 없어 고정 응답으로만 흐름을 확인했다. 키를 `.env.local`에 넣은 뒤 info.png와 실제 대상 도면으로 두 공급자를 실행해 추출 품질·토큰·비용·시간을 기록해야 완료 기준을 충족한다. GPT 기본 모델 ID(`gpt-6.2-astra`)는 OpenAI 모델 문서 기준이며, 검색 결과 중 `gpt-6-astra`를 가리키는 자료도 있어 첫 호출 때 확인한다.
- info.png는 축척이 일정하지 않은 설명용 이미지라(상단 5m·10m·3m 구간의 px/m가 서로 다름) 치수 충돌 표시 검증에는 적합하지만 좌표 정확도 평가에는 쓸 수 없다.
- 단일 호출 방식이라 모델이 이미지를 잘라 확대해 보며 확인하지 않는다. 조밀한 도면에서 정확도가 부족하면 잘라 보기 도구를 주는 방식을 S5 평가 후 검토한다(단기 범위의 "자율 Agent 미도입" 원칙과 함께 판단).
- 한도(동시 실행·시간당 요청)는 서버 프로세스 메모리에만 있으므로 여러 인스턴스로 배포하면 공유 저장소가 필요하다. 사용자 인증이 없어 공개 배포 시 누구나 호출할 수 있다(L5 계정·권한과 함께 해결).
- 기둥·영역·벽 높이는 추출하지 않는다. 대각선 벽은 맞춤만 하고 펴지 않는다.

### S5. 평가와 첫 배포 준비

- [ ] 실제 대상 도면으로 평가 세트를 구성한다. 깨끗한 축척 도면, 미표기 높이, 치수 충돌, 미지원·저품질 입력을 포함한다.
- [ ] 벽 위치 오차, 문·창 누락/오검출, 치수-구간 연결 정확도, 수동 수정 횟수·시간, 처리 시간·비용을 측정한다.
- [ ] 기준 샘플과 채점 방법을 먼저 고정하고 초기 평가 후 배포 허용 기준을 문서화한다. 아직 측정하지 않은 정확도 수치를 약속하지 않는다.
- [ ] 기존 타입 검사·사무실 검증에 입력 검증·좌표 변환·저장 왕복 검증을 추가한다. `verify-office.ts`는 사무실 회귀 검증으로 유지하고, 일반 도면용 검증 스크립트를 별도로 둔다.
- [ ] 실제 업로드·수정·도면 교체를 브라우저에서 검증하고 WebGPU 및 WebGL 2 경로의 결과를 기록한다.

완료 기준: 기존 예제와 별개의 도면에서 전체 흐름이 재현되고, 인식 한계·미확정값·수동 보정 방법을 설명할 수 있다. 단기 완료는 S1~S5 전체를 의미한다.

## 7. 제안 구현 경계와 의존 관계

```text
입력 UI / 이미지 분석 서버
        ↓
FloorPlanDocument + 원본 근거 + 검증 결과
        ↓
2D 편집 상태와 변경 이력
        ↓
장면 변환 어댑터
        ↓
기존 SceneConfig → 2D / 3D / 충돌 / 미니맵
```

편집 문서가 원본 상태를 소유하고 Three.js 객체는 표현 결과로 취급한다. AI 분석과 장면 변환을 분리하여 모델 교체가 렌더러 변경으로 이어지지 않게 한다.

S1 → S2 → S3 → S4 → S5 순으로 진행한다. S3은 수동 변환의 중간 배포 지점이며, S4의 AI 자동 추출까지 구현되었다고 표시하지 않는다. 업로드·분석 서버와 Next.js 경계를 구현하기 전에 설치된 `node_modules/next/dist/docs/`의 관련 가이드를 확인한다.
