## 1. 권장 개발 방향

**기존 거실 프로토타입은 `/`에 유지하고, 사무실 2안을 `/office`에 추가한다.** 렌더러, 품질 설정, 에셋 로딩, 조명 관리, 오류 처리 등은 재사용한다. 공간 설정과 새 가구만 확장한다.

기존 `ROOM` 값을 6 × 5m에서 18 × 8m로 바꾸는 것만으로는 충분하지 않다. 현재 코드에는 거실 전용 전역 설정, 실내 카메라 제한, 여섯 표면에 대한 라이트맵, 단일 환경맵이 서로 연결되어 있다. 따라서 먼저 장면별 설정을 전달하는 경계를 만든 뒤 사무실을 추가한다.

첫 목표는 **이미지의 공간 구획·가구 수량·배치·조감도 재현**이다. 기존 AO와 조명 기능을 활용하고, SSR 개선이나 새 전역 조명 구현은 배치 작업과 분리한다.

## 2. 조사 범위와 현재 구현

`AGENTS.md`, 기존 계획과 README, 패키지 설정, 장면·가구·카메라·재질·리소스·베이크·환경맵·상태 관리 코드를 확인했다. 이 문서 작성 중 앱 실행, 브라우저 확인, 성능 측정은 하지 않았다. README의 기존 측정값은 이전 구현의 기록이며 새 사무실 성능을 의미하지 않는다.

### 기존 구현을 보존할 항목

- `/`의 기존 거실 배치, 기본 카메라, 시점 버튼과 조작 방식
- `?backend=webgl`을 통한 강제 대체 실행
- 낮음·보통·높음 품질, 노출·톤 매핑·효과 토글
- 로딩 단계·실패·지원 불가·모델 누락 안내
- GLB 캐시 원본을 옮기지 않고 복제하는 처리

기존 기능을 보존한다는 의미는 파일을 모두 수정하지 않는다는 의미가 아니다. 공용 코드 변경이 필요하면 기본 인자를 기존 거실 값으로 유지하고, 거실 동작을 함께 검증한다.

## 3. 첨부 이미지 분석

이미지는 왼쪽의 2D 배치도와 오른쪽의 3D 조감도로 구성되어 있다. 가구 색상·배치·구획을 참고할 수 있지만, 시공 도면이나 정확한 축척의 CAD 자료로 취급하지 않는다.

### 공간 구성

| 영역 | 이미지에서 읽을 수 있는 내용 | 해석 수준 |
| --- | --- | --- |
| 전체 | 가로 구간 5.0 + 10.0 + 3.0m, 왼쪽 깊이 8.0m | 표시 치수. 전체 18 × 8m를 초기 기준으로 제안 |
| 대회의실 | 왼쪽의 긴 공간, 세로 방향 회의 테이블, 14인석 | 영역과 좌석 수 명시 |
| 메인 업무공간 | 중앙 상단, `10 × 4m`, H형 ①·② | 영역과 데스크 두 세트 명시 |
| 소회의실 | 중앙 하단 왼쪽, `6인석`, 하단 가로 3.6m 표시 | 좌석 수와 가로 치수 명시, 깊이는 추정 |
| 오픈 미팅공간 | 중앙 하단, `4 × 4m`, 원형 테이블 두 개 | 영역과 수량 명시 |
| 휴게라운지 | 오른쪽 상단, `3 × 3.6m`, 소파·원형 낮은 테이블·암체어 | 치수와 주요 가구 확인 |
| 탕비 영역 | 오른쪽 하단, 싱크·상판·하부장·가전으로 보이는 물체 | 용도는 시각적 추정, 오른쪽 3.4m 표기와의 관계 확인 필요 |
| 입구 | 아래쪽 오른쪽, 업무·미팅 공간과 탕비 영역 사이 | 위치 확인, 문 폭·열림 방향은 모델링 가정 필요 |

### 수량과 좌석 해석

- 대회의실: 14석. 초기 배치는 긴 변 양쪽 각 6석 + 양 끝 각 1석으로 제안한다.
- 소회의실: 6석. 초기 배치는 긴 변 양쪽 각 2석 + 양 끝 각 1석으로 제안한다.
- H형 데스크: 정확히 2세트. 이미지상 세트당 의자 약 4개로 보이므로 총 8석으로 임시 구성한다. 업무 좌석 수는 이미지의 명시 치수가 아니므로 설정값으로 관리한다.
- 오픈 미팅: 원형 테이블 정확히 2개. 테이블당 의자는 약 3개로 보이므로 각 3석을 초기 가정으로 둔다.
- 휴게라운지: 소파 1개, 암체어 1개, 낮은 원형 테이블 1개.
- 회의실·업무·오픈 미팅 의자: 위 가정 기준 총 34개. 휴게 가구는 별도다.
- 서쪽 외벽에는 반복 창이 있다. 창 개수·폭·창 사이 구조물 크기는 표시 치수가 없어 시각적 가정으로 관리한다.

### 외관과 재질

- 바닥: 짙은 회색 카펫 또는 타일 계열로 보인다.
- 외벽: 밝은 아이보리, 창틀은 어두운 계열.
- 파티션: 밝은 프레임과 연한 청록색 유리.
- H형 데스크: 흰색 상판·수납부, 어두운 의자, 중앙 연결부.
- 회의 테이블: 밝은 목재 계열, 모서리가 둥근 직사각형.
- 원형 미팅 테이블: 흰색, 라운지 테이블: 따뜻한 목재색.
- 3D 시안은 천장이 없고 전면 벽이 낮아 내부가 보이는 조감도다.
- 청색 제목·화살표·영역명은 설명용 표식이다. 가구의 실제 표면 텍스처와 분리한다.

### 치수 충돌 및 확인이 필요한 항목

1. **오른쪽 세로 3.6 + 3.4m는 전체 8.0m보다 1.0m 짧다.** 빠진 공간이 통로인지, 치수의 기준 차이인지, 이미지 편집상의 오차인지 확인할 수 없다.
2. 중앙 업무공간 깊이 4m와 오픈 미팅 깊이 4m는 전체 8m에 맞지만, 벽 두께가 포함된 값인지는 알 수 없다.
3. 중앙 하단의 3.6 + 4.0m를 제외하면 중앙 가로 10m 중 2.4m가 남는다. 이를 입구 연결 공간으로 사용하는 것은 개발 제안이다.
4. 창·출입문·유리문·H형 데스크의 정확한 치수와 벽 높이는 표시되어 있지 않다.
5. 이미지의 픽셀 비율과 표시 치수가 완벽히 일치하지 않는다. 픽셀을 단일 배율로 환산해 전체 좌표를 확정하지 않는다.

확정 가능한 수량과 영역 관계부터 구현하고, 위 항목은 설정으로 조절할 수 있게 한다. 우선 표시 치수를 따라 블록 배치를 만든 뒤 이미지와 시각적으로 조정한다.

## 4. 초기 공간 좌표 제안

### 좌표 규칙

- 단위: 1 = 1m. 기존 프로젝트와 동일하다.
- 도면 좌표 `(u, v)`: 외곽 기준 왼쪽 위가 `(0, 0)`, 오른쪽이 `+u`, 아래가 `+v`.
- 3D: `+Y`가 위, 서쪽 `-X`, 동쪽 `+X`, 북쪽 `-Z`, 남쪽 `+Z`.
- 초기 변환: `x = u - 9`, `z = v - 4`, 바닥 `y = 0`.
- 가구 위치는 기존 `FurnitureItem`과 동일하게 바닥 중심이다. 회전은 Y축 도 단위다.
- 아래 영역 경계는 공간 배분을 위한 기준선이다. 외벽·유리·문틀 두께와 실제 유효 폭은 이후 안쪽으로 조정한다.

### 영역 배분 초안

| ID | 영역 | u 범위 | v 범위 | 기준 크기 | 주의점 |
| --- | --- | --- | --- | --- | --- |
| `large-meeting` | 대회의실 | 0–5 | 0–8 | 5 × 8m | 이미지 가로 5m 구간 사용 |
| `work-area` | 업무공간 | 5–15 | 0–4 | 10 × 4m | H형 두 세트 |
| `small-meeting` | 소회의실 | 5–8.6 | 4–8 | 3.6 × 4m | 깊이 4m는 개발 가정 |
| `open-meeting` | 오픈 미팅 | 8.6–12.6 | 4–8 | 4 × 4m | 테이블 두 개를 대각 배치 |
| `entry-circulation` | 입구 연결 | 12.6–15 | 4–8 | 2.4 × 4m | 실로 막지 않는 연결 공간 |
| `lounge` | 휴게라운지 | 15–18 | 0–3.6 | 3 × 3.6m | 이미지 명시 크기 |
| `right-buffer` | 미확정 조정 구간 | 15–18 | 3.6–4.6 | 3 × 1m | 치수 차이를 보류하는 자리. 실제 통로라고 단정하지 않음 |
| `pantry` | 탕비 영역 | 15–18 | 4.6–8 | 3 × 3.4m | 깊이 표기 해석을 위한 임시 위치 |

`right-buffer`는 별도의 닫힌 방으로 만들지 않는다. 초기에는 라운지·탕비 입구 주변의 열린 조정 공간으로 두고, 실제 기준이 확인되면 재분배한다. 면적 합계 144㎡는 이 초안의 수학적 합계이며 실측 면적이 아니다.

```text
북쪽 / v=0
┌─────────────┬─────────────────────────────────┬─────────────┐
│             │  H형 ①           H형 ②          │ 휴게라운지  │
│ 대회의실    │          메인 업무공간          │             │
│ 14석        │                                 ├─ 조정 구간 ┤
│             ├───────────┬─────────────┬───────┤             │
│ 긴 테이블   │ 소회의실  │ 원형 ○      │ 입구  │ 탕비 영역   │
│             │ 6석       │      ○     │ 연결  │             │
└─────────────┴───────────┴─────────────┴── 입구┴─────────────┘
남쪽 / v=8
```

도식은 공간 관계 설명용이며 정확한 축척이나 문 위치를 나타내지 않는다.

### 주요 가구 앵커 초안

`중심(u,v)`를 위 변환식으로 3D에 전달한다. 치수와 위치는 이미지 재현을 위한 초기값이며 실측값이 아니다.

| 가구 | 중심(u,v) | 초기 크기 | 비고 |

| H형 ② | (12.0, 2.0) | 전체 폭 3.2 × 높이 0.74 × 깊이 3.0m | 세트 사이 동선 확인 |

회의용 의자는 테이블 다리와 겹치지 않게 좌석 배열에서 생성한다. 가구의 바운딩 박스뿐 아니라 의자를 뒤로 빼는 공간·문 열림 영역·입구에서 각 공간까지의 연결을 함께 확인한다. 통로 여유는 초기 배치 파라미터로 두며, 이 문서에서 법정 유효 폭이나 시공 적합성을 확정하지 않는다.

## 5. 기존 구성품 재사용과 추가 제작

### 재사용 가능 범위

| 현재 구성품 / 코드 | 사무실 활용 | 필요한 작업 |
| --- | --- | --- |

### 추가해야 하는 최소 구성품

| --- | --- | --- |

H형 데스크는 단순 직사각 책상 두 개로 대체하지 않는다. 이미지에서 읽히는 H자 실루엣을 우선 구현한다. 의자·모니터 등은 독립 배치 항목으로 생성해 2D 수량 표시와 베이크 차폐에도 반영한다. 그룹이 생성한 자식 가구를 다시 별도 배열에 중복 등록하지 않는다.

`FurnitureKind`가 늘면 `ProceduralModels.tsx`의 `Record<FurnitureKind, ...>` 등록도 같은 변경에 포함한다. 타입만 늘리고 기본 모델을 빼먹으면 컴파일 또는 GLB 실패 시 동작이 깨진다. 새 모델 구현은 `OfficeModels.tsx`로 나누어 기존 가구 함수의 의미를 유지한다.

## 6. 기존 기능을 보존하는 구조 확장

### 장면 설정을 전달하는 최소 경계

1. 기존 `src/config/interior.ts`는 거실 설정으로 계속 유지한다.
2. 공통 타입이 필요하면 별도 `sceneTypes.ts`로 옮기고 기존 파일에서 다시 export해 기존 import 경로를 보존한다.
3. `officePlan.ts`에는 도면상의 영역·벽·개구부·가구 그룹·주석·치수만 정의한다.
4. `officeLayout.ts`에서 도면 좌표를 3D 좌표로 바꾸고 실제 가구 목록을 만든다. 이 결과가 장면·베이커·2D의 기준 데이터가 된다.
5. 공용 함수는 장면 설정을 인자로 받고, 기존 호출은 거실 기본값을 사용하게 한다.
6. 전역 `activeScene` 변수를 변경해서 전역 상수를 바꿔 읽는 구조는 사용하지 않는다.

장면 설정은 최소한 `id`, `room`, `furniture`, `partitions`, `lighting`, `bake`, `camera`를 가진다. 설명용 표식과 표시 모드도 장면 설정과 연결하되, 매 프레임 변하는 카메라 값은 여전히 참조와 R3F 루프에서 관리한다.

### 리소스와 상태 관리

- 초기에는 `/`와 `/office` 각각 하나의 Canvas만 사용한다.
- 장면 ID를 기준으로 장면·리소스가 재마운트되게 하고 이전 비동기 작업은 취소 표시를 확인한 뒤 결과를 폐기한다.
- 사무실 리소스 정리 시 거실이나 GLB 캐시의 공유 리소스를 잘못 해제하지 않는다.
- 기존 zustand 전역 저장소를 유지한다면 `resetForScene` 같은 진입 초기화 경계를 추가한다. 시점 ID, viewRequest, 로딩 단계, 경고, 통계, 장면 기본 강도를 함께 정리한다.
- 품질·효과 설정의 유지 정책을 정하되 WebGL 2에서는 기존 SSR 기본 비활성 정책을 유지한다.
- `/` → `/office` → `/` 왕복 시 사무실 시점이나 밝기가 거실에 남지 않는지 확인한다.
- 재질별 색상 변경은 기존 tinted 캐시 또는 장면 소유 복제본을 사용한다. 거실 기본 재질 값을 사무실 색으로 덮어쓰지 않는다.

이 단계에서는 범용 편집기나 별도의 3D 엔진 구조까지 만들지 않는다. 정적인 장면 두 개를 안전하게 구성할 정도로 확장한다.

## 7. 외벽·파티션·개구부와 단면 표현

### 벽과 구획 데이터

사무실 파티션은 임의 메시 좌표가 아니라 시작점·끝점·높이·두께·재질·개구부를 가진 선분으로 정의한다. 같은 선분에서 2D 벽과 3D 프레임을 생성한다.

- 대회의실 동쪽: 유리 파티션과 실제 출입 개구부.
- 소회의실: 북쪽·동쪽을 중심으로 이미지와 같은 유리 구획, 문 또는 열린 진입부.
- 라운지·탕비: 이미지의 밝은 벽과 유리 구획을 구분. 미확정 조정 구간은 막지 않음.
- 남쪽 외벽: 입구 위치에 실제 개구부.
- 서쪽 외벽: 반복 창.

문은 벽 위에 붙이는 장식으로 끝내지 않는다. 외벽에서는 기존 `WallOpening.kind`가 `window`만 지원하므로 문 타입과 개구부 생성 경로를 추가해야 한다. 바닥에 닿는 문 개구부는 벽 분할이나 외곽 윤곽 잘라내기로 처리하고, 바닥에 걸친 구멍을 일반 내부 hole처럼 넣어 생기는 퇴화 형상을 피한다. 문짝의 힌지·열림 각·문틀은 개구부와 같은 기준을 사용한다.

문 위치는 이미지 근처로 제안하되 각 폐쇄 공간이 연결 동선에서 접근 가능하도록 정한다. 문을 만들고도 닫힌 파티션을 중복 배치하는 문제를 검사한다.

### 조감도와 실내 보기

| 모드 | 벽·천장 | 카메라 | 목적 |
| --- | --- | --- | --- |
| 사무실 조감도 | 천장 숨김, 전면 벽 낮춤 또는 숨김, 창이 있는 서측·북측 벽 유지 | 외부 높은 시점 | 첨부 3D 시안 재현 |
| 사무실 실내 | 전체 벽 높이·필요한 천장 표시 | 실내 프리셋 | 기존 탐색 방식 활용 |
| 거실 | 기존 표현 그대로 | 기존 실내 경계 | 기존 기능 보존 |

사무실 기본은 조감도다. 자동으로 카메라 방향마다 벽을 숨기는 기능은 후속으로 두고, 우선 지정한 단면으로 일관되게 표현한다.

중요: Three.js의 `visible=false`만으로 벽을 숨기면 일반적으로 그 벽의 그림자도 사라진다. 조감도는 열려 있는 모형에 맞는 밝은 프레젠테이션 조명을 사용한다. 실내 모드는 닫힌 구조에 맞는 조명·베이크를 사용한다. 조감도에서 벽을 감춘 채 기존 실내 베이크가 물리적으로 동일하다고 설명하지 않는다. 첫 구현은 별도 모드 설정과 검증된 리소스 갱신으로 처리하고, 복잡한 그림자 전용 대체 메시 처리는 필요할 때만 추가한다.

### 유리 재질

- 기존 창 유리와 별도로 청록색 `officePartitionGlass`를 추가한다.
- 초기에는 낮은 불투명도의 단순 투명 재질과 명확한 프레임으로 구현한다.
- 겹친 유리의 정렬·깊이·깜빡임을 확인하고 중복 면을 피한다.
- 고비용 transmission이나 굴절은 기본 요구로 두지 않는다.
- 2D 유리선과 3D 유리 면의 위치가 같은 파티션 데이터에서 나오게 한다.

## 8. 카메라와 2D·3D 화면

### 조감도 카메라

현재 카메라의 최대 거리 4.6m, 높이 최대 2.55m, 실내 위치 제한은 18 × 8m 사무실 조감도에 맞지 않는다. 해당 값은 거실에 남기고 사무실에는 별도 프리셋을 둔다.

- 초기 외부 시점 예: `[18, 18, 23]`, 타깃 `[0, 0.5, 0]`. 정확한 값은 화면 비율과 전체 바운딩 박스로 맞춘다.
- 사무실 기본은 직교 카메라를 우선 검토한다. 첨부 이미지의 평행한 선과 배치 비교에 적합하다.
- 최종 프레이밍은 고정 좌표만 믿지 말고 전체 가구·벽의 bounds와 뷰포트 비율로 계산한다.
- 대표 시점: 전체, 대회의실, H형 데스크, 소회의실, 오픈 미팅, 라운지.
- 실내 모드에서만 카메라를 방 내부로 제한한다.
- 투영 카메라가 교체되면 Controls와 AO·SSR 후처리의 카메라 참조도 갱신한다. 동일한 Effects가 계속 이전 카메라를 참조하지 않도록 한다.
- 화면 분할·크기 변경 시 직교 카메라 범위나 줌을 다시 계산한다.

### 첨부 이미지 전체를 재현하는 화면 제안

- `/office`에서는 흰 배경 위에 2D 배치도와 3D 시안을 함께 보여 주는 비교 화면을 제공한다.
- 2D는 SVG로 구현하고 3D는 기존 R3F Canvas를 사용한다. 초기에는 두 개의 WebGPU Canvas를 만들지 않는다.
- 두 화면은 동일한 영역·벽·문·가구 데이터를 사용한다. SVG를 이미지처럼 따로 손으로 그려 좌표가 달라지게 하지 않는다.
- 2D에는 공간 이름, 주요 치수, 입구, H형 ①·②를 표시한다.
- 3D에는 H형 ①·②와 입구 등 필요한 설명만 HTML 오버레이로 표시한다. 메시에 글자를 굽지 않는다.
- 이미지의 `2안`·화면 제목·남색 표식은 프레젠테이션 UI로 구성한다. 거실의 기본 UI는 유지한다.
- 렌더링 설정과 통계 기능은 유지하되 사무실 비교 화면에서는 접거나 필요 시 열 수 있게 한다.
- 좁은 화면에서는 2D·3D 탭 전환 또는 세로 배치를 제안한다. 모바일 성능·조작 검증은 별도로 진행한다.

SVG 좌표 변환은 미터 단위 viewBox를 기본으로 하고, 모델별 실제 footprint를 투영한다. 원형 테이블은 원으로, 회전 가구는 회전된 footprint로, H형 그룹은 H자 실루엣으로 그린다. 의자와 치수선·문 열림 호를 함께 표시해 가구 충돌을 확인할 수 있게 한다.

## 9. 조명·재질·성능 변경

### 조명 재사용 범위

- 기존 방향광과 품질별 그림자 해상도 설정을 재사용한다.
- 거실의 `shadow.cameraExtent = 5.5`, `far = 25`를 그대로 쓰지 않는다. 사무실 전체 bounds를 광원 좌표로 변환해 그림자 범위를 다시 맞춘다.
- 조감도에서는 밝은 외부 표현을 우선하고, 실내 모드에서는 반복 창과 실내 조명을 반영한다.
- 업무 조명은 소수의 광원으로 시작한다. 의자나 데스크마다 그림자 광원을 만들지 않는다.
- 기존 램프 토글은 사무실 실내등 그룹에 연결하고, 발광 표면과 실제 광원이 함께 바뀌게 한다.
- 짙은 바닥은 높은 거칠기로 시작한다. 유리·바닥 반사를 과하게 키우지 않는다.

### 베이크 및 환경맵 제한

현재 베이커는 외곽 여섯 면에 대한 해석적 근사다. 내부 파티션의 정확한 광선 차폐나 여러 방 사이의 광 전달을 계산하지 않는다. 파티션을 가구 차폐 목록에 넣는 것만으로 정확한 빛샘 해결이 되지는 않는다.

초기 사무실은 다음 순서로 처리한다.

1. 외곽 여섯 면은 장면별 설정을 전달받는 기존 라이트맵 경로를 재사용한다.
2. 파티션과 새 가구는 기본 재질·직접광·환경광·AO로 표현한다. 존재하지 않는 파티션용 라이트맵을 참조하지 않는다.
3. 정밀 실내 조명이 필요해지면 임의의 표면 ID, 표면별 UV·베이크·재질 연결을 추가하고 실제 베이크 또는 구획을 고려한 계산으로 확장한다.
4. 조감도·실내 모드의 베이크 전제를 분리하고, 장면·구획·광원·재질·베이크 설정이 달라지면 캐시를 무효화한다.

환경맵도 현재의 따뜻한 목재 거실 상자를 사무실에 그대로 사용하지 않는다. 사무실의 회색 바닥, 밝은 벽, 반복 창, 주요 가구 실루엣을 반영한 간단한 캡처를 만든다. 처음에는 하나의 사무실 환경맵으로 시작하고, 여러 방의 지역 반사와 박스 투영은 별도 후속 작업으로 둔다.

SSR은 기존 실험 기능으로 보존한다. 이번 재구성의 완료를 SSR 개선이나 미병합 Three.js 기능에 의존시키지 않는다.

### 성능 예산

- 바닥 면적은 기존 30㎡에서 초안 144㎡로 4.8배가 된다. CPU 베이크는 면적뿐 아니라 창 샘플 수·광원 수·가구 차폐 수의 영향도 받는다.
- 첫 배치 작업은 라이트맵 텍셀 밀도를 낮춘 사무실 전용 초안 품질로 진행하고 결과를 보고 조정한다.
- 같은 의자 34개를 모두 고유 지오메트리·재질로 만들지 않는다. 공유 지오메트리와 필요 시 부품별 인스턴싱을 사용한다.
- 동일 가구 그룹의 디테일은 멀리서 보이는 정도에 맞춘다. 캐스터·키보드 등은 초기에는 단순화한다.
- 유리 중복 면과 투명 물체의 겹침을 줄인다.
- 환경맵 캡처와 베이크는 장면 준비 시 수행하고 매 프레임 재생성하지 않는다.
- 새 장면의 FPS·프레임 시간·드로콜·삼각형·텍스처 수·초기 준비 시간을 측정한다. 기존 README의 60 FPS를 사무실 보장값으로 사용하지 않는다.
